# TypedTXTemplate —— 规范总览

## 本规范是什么

TypedTXTemplate 定义如何把一份**带类型、自描述的载荷**放进比特币 SV 的一个交易输出，使得：

- 每一种动作都有它自己的**帧类型**（tag）；
- 每个类型都声明一份**有序、命名的字段结构**；
- 载荷是**不可变的**（被交易 id 承诺，可永久举证）；
- 该输出仍然是**普通可花费的 UTXO**，由声明的所有者控制；
- 任何独立实现都能解析它，并产出**逐字节相同**的输出。

一行形式：

```
<marker> OP_DROP   (<field> OP_DROP)*   <ownerPub(33)> OP_CHECKSIG
```

**永不产生 `OP_RETURN`。** 载荷改为承载在锁定脚本里，并且在签名检查之前被丢弃，因此不影响可花费性。

**不在范围内 —— 有意排除，一个符合本规范的实现完全不需要它们：**

| 不涵盖 | 这属于谁的职责 |
|---|---|
| 获取区块、区块头、交易、mempool 内容 | 传输层。符合规范的实现**从不接触网络**。|
| **发现**帧 —— 扫地址历史、给论坛建索引、列出帖子 | 索引服务。格式只规定*帧是什么*，从不规定*帧在哪里*。|
| 判断一个帧是否仍未被花费、是否已被第二笔交易认可 | 链上状态。核心只孤立地解析单个输出脚本。|
| UTXO 跟踪、钱包密钥派生、余额 | 钱包。|
| 广播交易 | 传输层。|
| 价格协商、报价的传输、链下正文的投递 | 应用 / 链下。子协议**可以命名**这些，但格式本身不编码它们。|

**必须记住的推论。** 一个格式完全正确的帧，你完全可能根本不知道它存在。本规范**不保证**一个帧存在、
它曾被打包、有人能找到它，或者它的字段曾被投递过。对*存在性*与*认可*的验证属于链上状态，归索引服务管。

## 跨仓库边界

本仓库**只做格式**。同生态下的通信协议由
[bsv8/ChannelProtocol](https://github.com/bsv8/ChannelProtocol) 负责
（`bsv8.*.v1` 协议族，含询价、消息投递、端到端加密信封）。两者职责不重叠：

| 仓库 | 负责 | 不负责 |
|---|---|---|
| TypedTXTemplate | 一个输出脚本的字节布局与验证 | 网络、索引、广播、通信 |
| ChannelProtocol | 消息如何发、验、去重、重试 | 链上脚本长什么样 |

## 关键词

本文中的**必须**、**禁止**、**应当**、**不应当**、**可以**，含义对应 RFC 2119 的
`MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY`。

- **规范条款。** `core/` 下的全部内容都是规范条款：两个符合规范的实现，对同一输入**必须**产出相同字节，
  并且**必须**接受完全相同的一组脚本。
- **非规范条款。** 标注为 *注*、*理由*、*提示* 的段落只解释意图，可以不提升帧类型版本号就修改。
