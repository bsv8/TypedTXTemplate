# 应用协议（子协议）

**应用协议**是建立在核心层之上的应用。核心层规定一份类型化载荷**如何编码**、**如何成帧**；
应用协议规定某个特定的帧**是什么意思**。

`bbs` 应用协议 —— 一个论坛 —— 是完整的实例：[`subprotocols/bbs/`](bbs/)。

## 1. 应用协议能添加什么

| 应用协议**可以** | 规定位置 |
|---|---|
| 注册一个新的帧类型 | [`core/registry.md`](../core/registry.md#3-申请标签) |
| 定义规范消息及其签名 | 自己的文档 |
| 为一条逻辑记录定义多笔交易的生命周期 | 自己的文档 |
| 定义一个基于链上状态的有效性判定 | 自己的文档，并注明*对核心层非规范* |
| 公布由 520 字节限制推导出的字节预算 | 自己的文档 |

| 应用协议**禁止** | 原因 |
|---|---|
| 重新解释核心层的框架、编码或字段类型 | 核心层就是规范格式 |
| 依赖某个帧能被找到、被打包、或处于存活状态 | 见 [§4](#4-应用协议不能依赖什么) |
| 给单个字段或整个帧加上超过 520 字节的内容 | 共识无效；见 [§5](#5-超过-520-字节) |
| 依赖一笔费用、一个身份或一次认可存在于链上状态中 | 链上状态不是格式的一部分 |

## 2. 格式与规则的切分

每份应用协议文档**应当**把两件事分开，并标明各自属于哪一类：

- **格式（规范条款）。** 字节布局、字段宽度、规范消息、签名域。两个符合规范的实现
  **必须**在这些字节上一致。
- **规则（应用层）。** 什么让一条记录变得可接受：谁可以发帖、价格可以是多少、
  一条记录何时算被认可、索引方必须列出什么。这些是叠加在字节之上的约定，
  属于应用协议自己的事务。

**留这条边界不明的应用协议，会导致一个具体且常见的 bug：** 实现发版后宣称完全合规，
而它的验证器会静默接受其他实现都不认为合法的帧 —— 因为它只抄了字节解析器，没抄规则判定器。

## 3. 命名

| | |
|---|---|
| 应用协议目录 | 全小写、连字符分隔，如 `bbs/` |
| 文档 | `v<主版本>-<主题>.md`，如 `v1-post.md` |
| 注册表标签 | `BSV8:<TYPE>:<MAJOR>.<MINOR>` |

应用协议的新主版本获得自己的 `v<n>-*.md` 文档组。旧的那一组**原样保留**在仓库中，
以保证历史帧始终可解码。

## 4. 应用协议不能依赖什么

这是塑造这里每一个设计的约束，所以值得把话说直：

> **帧只是一种形状。** 它是否存在、是否有人找得到、是否算数，全都是链上状态或链下的事实，
> 没有一个是本规范的一部分。

具体地，应用协议**禁止**假定：

- **可被发现。** 格式里没有任何东西说明帧在哪里。核心层从不执行任何查找。
  如果一个应用协议需要帧可被发现，它**必须**把发现约定记录为*对索引服务的范围外依赖*，
  并且读规范的人**必须**能把这两者区分开。
- **永久性。** 该输出是可花费的，所以帧可以离开 UTXO 集。见
  [core/encoding.md §1](../core/encoding.md#1-为什么不用-op_return)。
- **存在性。** 一个格式正确的帧**不能证明**它曾被广播或被打包。
- **认可。** 第二笔交易里的第二个签名是一种*约定*。核心层孤立地解析每个输出，
  **不会**把它们关联起来。

一个想要"运营方已批准此条"这一性质的应用协议，因此只有两条路：
要么接受某个索引服务作为事实来源，要么把这份批准做成**单个帧之内的一个字段**。
这个取舍以字节计量，写在 [`bbs/v1-post.md`](bbs/v1-post.md) 里。

## 5. 超过 520 字节

一个帧的整个脚本必须装进 520 字节。当应用协议需要更多时，选项按优先级排列：

1. **对它取哈希。** 链上放 32 字节摘要，正文放在该应用协议自己的投递通道里。
   `bbs` 就是这么做的，这也正是为什么一个 `bbs` 帖子所承诺的文档可以比帧本身大。
2. **缩短它。** `hash256` → 16 字节，`u64le` → `u32le`，删掉一个字段。省下的每个字节都是正文的字节。
3. **拆分它。** 多帧，用父引用串联。`bbs` 用 `parentHash` 串联；这同时也恰好建模了论坛的楼层结构。

拆分是唯一在规模上不受限的选项，也同样是唯一会增加生命周期的选项 —— 一个横跨两帧的文档
需要一条规则说明它何时算完整。这条规则在链下，因此**无法从格式验证**。

## 6. 签名与域分离

签名的应用协议**必须**使用一个标明应用协议、版本与角色的域分离前缀，
使得为某个目的产生的签名**永远无法**被当作另一个目的重放：

```
SHA256d("bsv8/<子协议>/v<主版本>/<角色>|" ‖ <按 schema 顺序的字段，但不含 body>)
```

要求：

- 前缀**必须**逐字节精确并发布。不同语言的实现**必须**产出完全相同的前像。
- **每个不同角色必须拿到不同前缀。** 一个同时有作者签名和运营方签名的应用协议需要两个前缀；
  共用一个会让任何一方都能冒充另一方。
- 未纳入消息的字段**必须**在应用协议文档中显式列出，使"排除"永远不是猜测。
- 只用紧凑 64 字节签名
  （[core/field-encodings.md §2.1](../core/field-encodings.md#21-sig64-与-der)）。

**提示。** 对哈希签名，不要对拼接结果直接签名。长度依赖于变长字段的消息会产生长度不可预测的
签名前像；先哈希可以把被签名的长度固定为 32 字节，并消除一整类截断 bug。
