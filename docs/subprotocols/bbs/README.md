# 应用协议 `bbs`

`bbs` 是一个**论坛**应用协议，定义在 TypedTXTemplate 核心层之上。

## 1. 它是什么

`bbs` 定义两种业务模型，共用同一套帧格式与同一套证据链：

| | **公开 BBS** | **私密群** |
|---|---|---|
| 谁能读正文 | 任何人 | 只有持有某个私钥的成员 |
| 帧类型 | `BSV8:POST:1.0`（明文 `body`） | 密文信封 + `groupId` |
| 加密 | 无 | 密钥图广播加密 |
| 计费 | `fee` + `operatorSig` | 成员资格，不按帖计费 |
| 规范 | [v1-post.md](v1-post.md) | 私密群帧待定 |

两者的**格式层**（压栈、字段宽度、签名域）完全一致；差别只在正文是否加密。
公开 BBS 是先落地的部分。

## 2. 帧一览

| 标签 | 用途 | 规范 |
|---|---|---|
| `BSV8:POST:1.0` | 一个帖子或一条回复 | [v1-post.md](v1-post.md) |

只有**一种**帧。询价、报价、投递、索引、认证都不产生帧 —— 它们是**通信**，属于
[ChannelProtocol](#5-跨仓库边界)。

## 3. 文档

| | |

## 4. 范围

**在范围内（格式，规范条款）：** 帖子帧的字节布局、字段宽度、签名消息、域分离前缀、
以及不依赖链上状态即可判定的部分。

**在范围外（约定，本协议明确不规定）：**

| 事项 | 说明 |
|---|---|
| **询价与报价** | 属于 [ChannelProtocol](#5-跨仓库边界) 的 `bsv8.bbs.quote.v1` |
| **如何找到帖子** | 见 [§6](#6-寻址锚点约定) |
| **正文的投递与存储** | 链上只有 `body` 预览与 `postHash`；完整文档由索引方持有 |
| **哪些帖子被列出** | 索引策略 |
| **身份如何注册** | `posterPub` 只是一个公钥；它与任何身份系统的绑定是链下约定 |
| **链上状态查询** | 「已确认」「已被认可」都是索引服务的事 |

**必须明确的推论。** `bbs` 规范可以保证**一条记录的字节可被独立验证**；
它**不能**保证这条记录存在、找得到、或被任何索引方列出。这些是
[core/registry.md §5](../../core/registry.md#5-注册表的纪律) 里说的"注册不等于所有权主张"的具体化。

## 5. 跨仓库边界

| 仓库 | 职责 |
|---|---|
| **TypedTXTemplate**（本仓库） | `BSV8:POST:1.0` 的字节布局与验证规则。**没有**网络代码。|
| **[bsv8/ChannelProtocol](https://github.com/bsv8/ChannelProtocol)** | 询价、报价、消息投递。`bsv8.bbs.quote.v1` 定义在这里。|

两者的接口只有一处：**帖子的 `fee` 与 `notAfterHeight` 来自一次签名报价。**
TypeScript 一侧因此同时依赖两个包，这是刻意的 —— 格式与通信是两个正交的关注点，
把它们塞进一个包会让两边都无法独立演进。

## 6. 寻址锚点（约定）

要让帖子可被发现，需要一个"地址"约定。本协议**规定这个约定的标识**，
但**不规定**如何按它检索 —— 后者属于索引服务。

约定如下（**非规范，索引方与客户端自行达成一致**）：

发布一笔交易，其输出之一是 `1 sat` 的**标准 P2PKH**，支付给一个众所周知的板块注册地址；
同一笔交易的另一个输出是帖子帧本身。

> **为什么必须是两个输出。** 索引服务（含 ElectrumX 一类）按**输出脚本的精确哈希**索引。
> 只要往锁定脚本里加一个字节，脚本哈希就变了，按地址算出的哈希**永远匹配不上**。
> ElectrumX 协议没有模板匹配、没有通配索引、没有前缀查找 —— 它只认完整字节的哈希。
> 因此"能被地址命中"和"能携带数据"这两件事，只能由两个输出分别承担。
> 详见 [core/encoding.md §3](../../core/encoding.md#3-规范压栈编码) 关于"位置决定含义"的说明。

这个约定带来的性质是**范围外**的，规范在此只作记录：读者**不能**从本规范推断出任何检索能力。
