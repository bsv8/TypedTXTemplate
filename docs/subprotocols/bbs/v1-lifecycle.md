# `bbs` v1 —— 生命周期

规范条款与规则。一个 `BSV8:POST:1.0` 记录的生命周期包含**一次询价**和**两笔链上交易**。

## 1. 生命周期总览

```text
  ① 询价 ────────── 范围外：ChannelProtocol 的 bsv8.bbs.quote.v1
     │               得到一份签名报价：{ fee, notAfterHeight, quote_id }
     ▼
  ② 提议（链上第 1 笔）运营方在 body 里的 operatorSig 锁定 fee + notAfterHeight
     │               作者付 5 sat 给板块注册地址，同时发出 data output
     ▼
  ③ 认可（链上第 2 笔）作者花费 data output —— 花费签名即认可全部条款
```

只有 ② ③ 属于本规范。① 是通信，**不属于**任何帧类型。

## 2. 询价（在范围外）

**询价不产生链上帧。** 它是给运营方发一条消息，问"这个板块这一帖多少钱"。

| | |
|---|---|
| 协议 | `bsv8.bbs.quote.v1`，定义在 [bsv8/ChannelProtocol](https://github.com/bsv8/ChannelProtocol) |
| 形态 | 公开频道上的签名 CP 消息，任何人可读、可比较多家报价 |
| 报价内容 | `fee`（satoshi）、`notAfterHeight`（截止高度）、`boardId`、`quote_id` |
| 结算 | 走 SSP 的 billing，`request_id` 幂等 |

**为什么询价必须在外面。** 三条理由，每条都对应一个格式层无法承担的职责：

1. **它是通信，不是编码。** TypedTXTemplate 的全部内容是"一个输出脚本长什么样"。
   询价需要传输、重试、去重、有效期 —— 那是 ChannelProtocol 已经做好的事。
2. **运营方不该被链上数据绑架。** 一旦价格必须上链公告，价格就成了链上不可撤销的承诺；
   而链下签名报价**可以**在有效期内随便撤回或改价，链上那份只是最终承诺。
3. **它已经在协议族里存在。** ChannelProtocol v0.6.0 已有 `publicmessage` 原语、
   `hashrequest` 强类型签名请求、以及带 `request_id` 幂等的 SSP billing。
   询价是这三者的直接组合，**不需要**新造。

**接口只有一处**：报价里的 `fee` 和 `notAfterHeight` 被抄进帖子的同名字段，
然后被 `operatorSig` 锁定。格式层不需要知道报价是怎么来的。

## 3. 为什么认可要两笔

帖子帧的所有者是 `posterPub`。要让它同时表达"这是帖子"和"作者认可了这份条款"，
就需要两次签名动作：

| | 提议（proposal） | 认可（endorsement）|
|---|---|---|
| 谁签名 | 运营方（`operatorSig` 字段）| 作者（花费时的签名）|
| 承诺了什么 | `fee`、`notAfterHeight`、`postHash`、`posterPub` | `SIGHASH_ALL` → 整笔提议交易，含全部字段 |
| 效果 | 条款被锁定 | 条款被作者接受 |

**为什么"认可"可以省掉一个显式签名字段。** BSV 的 `SIGHASH_ALL` 承诺 `hashOutputs`，
也就是创建这笔交易时**所有输出**。作者在花费帖子帧时签下的签名，因此连带承诺了 `operatorSig`
里的每一个字节 —— 包括 `fee` 和 `notAfterHeight`。所以作者的花费签名**就是**对运营方条款的认可。

代价是：**未被花费的帖子没有作者认可。** 因此"必须花费"不是可选步骤，而是记录生效的条件。

## 4. 阶段一：提议

一笔交易，包含两个输出：

```
输入：作者的 UTXO
─────────────────────────────────────────────────────
输出[0]  1 sat   标准 P2PKH → 板块注册地址      ← 寻址锚点 + 索引服务费
输出[1]  1 sat   BSV8:POST:1.0 帧，owner = posterPub   ← 帖子
输出[2]  找零（若有）
```

两个输出**必须**在同一笔交易里，理由见 [README.md §6](README.md#6-寻址锚点约定)。

**推荐由作者出资。** 这让运营方成为一个纯索引服务，而不是一个签发者 ——
这与 [应用协议 §4](../README.md#4-应用协议不能依赖什么) 的范围划分一致，
也让 `fee` 的语义干净：它买的是索引服务，不是"购买被发布的权利"。

## 5. 阶段二：认可

作者构造并广播第二笔交易，其输入是帖子帧：

```
输入：输出[1]（BSV8:POST:1.0 帧）      ← 花费它 = 认可
─────────────────────────────────────────────────────
输出[0]  找零
```

**不可省略。** 一条从未被花费的帖子帧，其认可无法证明。

## 6. 确认与重组

| 状态 | 判定 | 属于 |
|---|---|---|
| 提议已广播、未进块 | 无 | 链上状态 |
| 提议已进块（`conf ≥ 1`）| 记录存在 | 链上状态 |
| 认可已进块 | 记录生效 | 链上状态 |
| 提议被重组掉 | 记录从未存在 | 链上状态 |

**建议成交门槛（非规范）：** 提议与认可各等 1 个确认后再视为成交。
原因是这两笔交易都存在被双花的窗口，而论坛记录的价值很低，不值得为此提高门槛。

## 7. 定价纪律

这是本文件里唯一一组**不能商量**的规则。

### 7.1 三层分离

| 层 | 由什么决定 | 能否撤销 |
|---|---|---|
| **① 内容有效** | `operatorSig` 验过 + 作者认可过 | **永远不能** |
| **② 商业有效** | `fee` vs 报价里约定的值 | 随报价变化 |
| **③ 索引展示** | 索引方政策 | 随时 |

`bbs` 规范保证的**只**是第 ① 层。价格只应当影响第 ② 层。

> **规则。** 索引方**禁止**因为"当前价格与本帖 `fee` 不同"而丢弃一条**内容有效**的记录。
> 唯一允许的处置是标注。

理由是直接的：运营方改一次报价，就能让全部历史帖子的链上证据全部作废。
那 `operatorSig`、那 64 字节、那套双签名机制就全部白设计了。
链上证据的价值，恰恰在于它**不能**被一个链下变量悄悄抹掉。

### 7.2 有效期用高度，不用时间

BSV 的 80 字节区块头**没有时间戳字段**（Genesis 升级后恒为 0）。所以：

| 想要的 | 能用 | 原因 |
|---|---|---|
| 楼层序号 | **块高度** | 不可伪造、不可重排（重组除外）|
| "3 小时前" | **不能** | 链上没有时间 |
| 按发帖时间排序 | 只能按高度 | 一个块内多笔交易的先后也不确定 |

所以 `notAfterHeight` 用高度而不是时间，是这个协议唯一可行的选择 ——
而且**高度是链上可验证的**：从 merkle 证明 + 区块头 + 头链推出，运营方说了不算。

### 7.3 窗口该定多长

BSV 出块间隔约 10 分钟。一个帖子的完整流程需要：运营方签名 → 作者审阅 →
作者构造并广播认可交易 → 等确认。**光是等 1 个确认就 10 分钟**，所以窗口不能是 2 个块。

| 窗口 | 实际时长 | 判断 |
|---|---|---|
| 2 块 | 20 分钟 | 不可行 |
| 50 块 | 8 小时 | 过紧 |
| **300 块** | **约 2 天** | **推荐** |
| 1000 块 | 约 7 天 | 宽松 |

`notAfterHeight` **必须**留出这段余量。给定一个当前高度 `H`，应不小于 `H + 300`。

**不设上限。** 运营方完全可以签一个 `notAfterHeight = 2³²−1`（永远有效），
等于自己放弃了涨价能力。规则不去堵它：**伤害的是运营方自己**，不值得防。

### 7.4 作废的正确手段

| 手段 | 是否允许 |
|---|---|
| 报价时给出较短的 `notAfterHeight` | ✅ 期限写在签名里，作者签约时已知 |
| 事后改报价，从而作废历史 | ❌ 禁止，见 §7.1 |
| 从索引结果中悄悄删除一条内容有效的记录 | ❌ 禁止。链上痕迹仍在，等于自证违规 |

### 7.5 索引方义务

以下是**规则**，不是格式条款：

1. 收录所有**内容有效**的记录（[v1-post.md §5](v1-post.md#5-验证) 通过），无论其商业状态。
2. 按 `postHash` 去重，保留**最早**的一笔。
3. 展示商业状态（当前报价 / 低于 / 高于 / 已过期），**不得隐藏其中任何一种**。
4. 核对 `fee` 与实际支付额。**冲突时以链上实际支付为准**，链上的 `fee` 仅作快速筛选。
5. 索引结果**必须**可被第三方用本规范独立重算 —— 不得引入只有索引方知道的私有过滤条件。

## 8. 费用构成

| 项 | 数量级 | 付给 |
|---|---|---|
| 提议交易的输出[0] | `fee`（= 报价值）| 运营方 |
| 提议交易的矿工费 | 约 1–400 sat | 矿工 |
| 认可交易的矿工费 | 约 1–100 sat | 矿工 |

**注（非规范）。** 在比特币 SV 上，单笔典型交易的手续费与一个普通交易的手续费同量级。
因此 `fee` 是一个**象征性门槛**（要花钱、要签名、无法免费批量），
它的作用是**反 spam**，不是价格发现，也不构成女巫成本。把 `fee` 定得很高不会让论坛更安全。

## 9. 验证流程（索引方）

以下是**规则**（应用层），不是格式条款。它需要链上状态，因此**不可**由一个孤立的帧验证器完成。

```
验证一条帖子记录：

1. 解析 → 运行 v1-post.md §5 的 verify()        （纯帧校验，必须通过）
2. 查 outpoint 的花费者                          （反向索引）
3. 若无花费者 → 状态 = 已提议，未认可
4. 有花费者 → 验其 scriptSig：
     a. 签名公钥 == 帧的 posterPub
     b. hashType == 0x41 (SIGHASH_ALL | SIGHASH_FORKID)
     c. SIGHASH_ALL 承诺的 hashOutputs == 提议交易的 merkle 计算结果
        （即：签名确实覆盖了本帧的全部字段）
5. 认可交易所在块高度 ≤ notAfterHeight → 有效；否则 → 过期
6. 按 §7.5 标注商业状态
7. 按需：反查输出[0]，核对实际支付额与 `fee` 是否一致
```

第 4 步的 (c) 是关键的加强：**只验"花费者的公钥等于 `posterPub`"是不够的**，
因为那不能证明签名者签的确实是这一帧。必须验 `hashOutputs` 的承诺关系。

## 10. 攻击面与对应的规则

| 攻击 | 防御 |
|---|---|
| 冒名顶替：构造 `posterPub` 指向受害者的帧，骗其花费 | 受害者在签名前审阅**整笔提议交易**（不只是这个输出）。`SIGHASH_ALL` 承诺全部输出，所以审阅是充分的。|
| 运营方事后改口价格 | `operatorSig` 覆盖 `fee` |
| 作者事后称不知价格 | 认可签名承诺 `hashOutputs` |
| 同一笔付款支撑多帖 | **每次提议都是一笔独立交易**；重复发布需重复付费。索引方按 `postHash` 去重。|
| 重放旧的认可 | UTXO 一次性 |
| 已过期帖子被当作有效报价 | 索引方**必须**按 `notAfterHeight` 标注 |
| 运营方改价清空历史 | §7.1 禁止 |

## 11. 规则的边界

明确**不在**本协议规定内：谁可以建板块、板块怎么关闭、是否需要预付、
spam 阈值、版主权限、争议仲裁，以及**询价的通信格式与传输**（§2）。
`bbs` 规定的是**一条记录的字节与证据结构**；运营方如何枚举、过滤、展示这些记录，
是它自己的服务政策。
