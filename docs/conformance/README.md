# 一致性测试

本规范的核心承诺是：**两个符合规范的实现，对同一输入必须产出相同字节，并必须接受完全相同的一组脚本。**
这个页面规定如何验证它。

## 1. 共享测试向量

[`vectors.json`](vectors.json) 是**唯一的真相来源**。它包含：

| 段 | 内容 |
|---|---|
| `kinds` | 每个帧类型的 schema、字段数、固定开销、body 上限 |
| `keys` | 固定的测试密钥对（**仅用于测试，绝不可用于任何真实资金**）|
| `signatures` | 域分离前缀、前像、`SHA256d` 后的消息、固定 `k` 的签名 |
| `frames` | 正例：完整脚本 hex + 期望的解析结果 |
| `parseRejections` | 负例：**必须**被解析器拒绝的脚本，附拒绝原因 |
| `semanticRejections` | 负例：**能解析但必须被验证器拒绝**的字段改动 |

**向量由一个独立于 Go 与 TypeScript 的第三方实现生成。** 三方独立实现产出同一批字节，
是比"两方互测"更强的检查。

### 固定 `k` 的原因

`signatures` 里的 `k` 是写死的。这是必要的：ECDSA 的 `k` 通常是随机的，
那会让签名向量每次生成都不同，无法作为回归基线。**固定 `k` 只用于测试向量**；
生产实现**必须**使用随机或 RFC 6979 派生的 `k`，且每次签名都要换
（见 [core/field-encodings.md §2.1](../core/field-encodings.md#21-sig64-与-der) 关于可延展性的说明）。

## 2. 两类失败必须被区分

这是本规范最容易被实现搞混的一点，因此单独列出：

| 失败类型 | 何时发生 | 实现应当 |
|---|---|---|
| **解析拒绝**（`parseRejections`） | 脚本**不是格式正确的帧** —— 字段数不对、缺 `OP_DROP`、非最短压栈、超过 520 字节 | 返回"不是帧"。**不得**返回部分填充的结果 |
| **语义拒绝**（`semanticRejections`） | 脚本**是**格式正确的帧，但**不满足该类型的规则** —— 版本不对、`fee` 为零、签名验不过 | 解析**必须成功**；验证步骤**必须**失败 |

混淆这两者的实现，会在真实数据上把"这条记录有问题"误报成"这不是我们的数据"，
从而静默漏掉记录。反过来，把语义检查塞进解析器，会让"能读出字段"和"接受这条记录"变成一件事，
使 `bbs` 那种"链上可见但商业无效"的记录无法被正确标注。

## 3. 差分测试框架

两套实现**各自**消费 `vectors.json`，然后比较结果。测试**不得**让一套实现去调用另一套。

```
                 vectors.json
                 ┌────┴────┐
                 ▼         ▼
          Go 实现        TypeScript 实现
          (go/)            (ts/)
                 │         │
                 └────┬────┘
                      ▼
              逐字节 / 逐字段比对
```

**必须比对的内容：**

| 项 | 比较方式 |
|---|---|
| 构建 `frames` | 产出的脚本 hex **逐字节**等于 `script` |
| 构建 `frames` | 产出的脚本**长度**等于 `scriptLen` |
| 解析 `frames` | 每个字段的值与类型与 `parsed` 一致 |
| 解析 `parseRejections` | 全部返回"不是帧" |
| 签名 | `sha256(preimage) == msg`，且 `sign(priv, msg) == sig` |
| 验签 | `verify(opPub, msg, sig) == true` |
| `semanticRejections` | 改动后的帧**能解析**，且验证步骤失败，原因与 `why` 一致 |

**字节序必须逐字节比对，不得"语义等价即通过"。** 例如 `fee` 的 `0x0500000000000000` 与
`0x0000000000000005` 在数值上相等，但只有前者是规范编码；`version` 的 `0x51`（`OP_1`）与
`0x0101` 在数值上也相等，但后者非最短，**必须**被拒绝。

## 4. 语言特定的坑

跨语言差分测试最容易在这些地方翻车，实现前请逐条对照：

| 坑 | 说明 |
|---|---|
| **无符号溢出** | Go 的 `uint32`/`uint64` 与 JS 的 `number` 行为不同。JS `Number` 只有 53 位精度，**无法表示 `u64le` 的完整范围**。`fee` 必须用 `BigInt` 或字节数组读写。|
| **字节序** | Go 的 `binary.LittleEndian` 与 JS 的 `DataView.getUint32(x, true)` 才对应。默认的大端会静默产生不同的字节。|
| **字符串与字节** | Go 的 `string` 是字节序列，JS 的 `string` 是 UTF-16。`utf8` 字段必须以字节为准处理；用 JS `String` 承载原始字节会经过有损转换。|
| **前导零** | `u32le` 的前导零是编码的一部分。`notAfterHeight = 3002` 是 `b2 0b 00 00`，**不是** `b2 0b`。|
| **切片别名** | Go 中 `make + append` 与 TS 中 `Buffer.concat` 的别名语义不同，容易在 `Push` 的追加逻辑里产生共享底层数组。|
| **负数** | `OP_1NEGATE` 编码的是 `0x81`，不是 `-1` 的补码表示之外的任何形式。解码后应还原为字节 `0x81`。|
| **最短压栈** | `Push` 与 `readPush` 必须是**严格互逆**的。任何一侧漏掉 `OP_0` / `OP_1`–`OP_16` / `OP_1NEGATE` 分支，两套实现就会在某一类输入上分叉。|

## 5. 必须自检的两条不变量

差分测试之外，每个实现还应当对自己的代码断言：

1. **`push(readPush(x)) == x`**，对所有合法输入 x。这是编码器的往返性质，
   能抓住绝大多数最短性错误。
2. **`parse(build(fields)) == fields`**，对随机生成的合法字段组合。
   建议至少 10⁴ 组随机输入，字段长度覆盖 `0, 1, 2, 16, 75, 76, 255, 256`。

这两条性质比任何固定的测试用例覆盖面都大，建议作为 fuzz 目标常驻。
