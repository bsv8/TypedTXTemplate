# 核心层 —— 脚本编码

规范条款。定义一份类型化载荷如何被物理地写进输出脚本，以及塑造这种编码的共识约束。

## 1. 为什么不用 `OP_RETURN`

在比特币 SV 上，`OP_RETURN` 已被 2020 年的 Genesis 升级从共识层移除。`OP_RETURN` 输出永远无法被花费，
因此产生它就等于销毁它所承载的价值；如果放任大规模使用，整个 UTXO 集最终会被抹掉。
在 BSV 上，包含 `OP_RETURN` 的交易是**共识无效**的。

对本规范的推论是绝对的：

> 符合本规范的实现，**禁止**在它构建的任何脚本中产生 `OP_RETURN`（`0x6a`）。

符合规范的*解析器*可以识别并拒绝 `0x6a`；实现也可以在本地校验时用它来拒绝某个脚本。
但它**绝不能**出现在自己产出的输出里。

**这带来的取舍。** 因为载荷位于一个可花费的输出中，载荷**不是永久记录**：该输出可以被花费，
载荷随之离开 UTXO 集。创建它的那笔交易永远存在，所以载荷仍然*可举证*，但它不再*存活*。
需要永久且不可花费记录的应用协议，无法用本核心表达 —— 见
[subprotocols/README.md](../subprotocols/README.md#4-应用协议不能依赖什么)。

## 2. 数据压栈惯例

载荷被写成一串**数据压栈**，每一个都在后续执行之前被丢弃：

```
<marker>  OP_DROP
<field₁>  OP_DROP
<field₂>  OP_DROP
……
<owner>   OP_CHECKSIG
```

这个形状带来三个性质，也正是它存在的理由：

1. **不可篡改。** 这些压栈属于*锁定脚本*。锁定脚本被交易 id 承诺，因此每个字段都绑定在一个
   无法修改、也无法否认的交易 id 上。
2. **不干扰可花费性。** 每个字段被压入后立即移除，所以到 `OP_CHECKSIG` 执行时，栈里只有
   `[…, ownerPub, 签名]`。签名检查看不到任何一个载荷字节。因此该输出是一个普通的可花费 UTXO。
3. **可被发现。** 这些压栈靠**位置**解析，而不是靠扫描魔法字节。长度前缀划定了每次压栈的边界，
   所以一份恰好包含 `0xac`（`OP_CHECKSIG`）、`0x4c`（`OP_PUSHDATA1`）或 `0x51`（`OP_1`）的载荷，
   永远不会被解释成代码。

**push 是一种编码，不是一条指令。** 在上面的例子里，只有 `OP_DROP` 和 `OP_CHECKSIG` 是操作码；
其余每一个字节要么是长度前缀，要么是载荷内容。

## 3. 规范压栈编码

一次压栈编码为**一个长度前缀 + 数据**。前缀按**最短**规则选择，而最短性是**共识要求**，
不是风格偏好：非最短压栈会被网络拒绝，报 *data push larger than necessary*。

| 数据长度 | 编码 |
|---|---|
| 0 | `OP_0` —— 单字节 `0x00` |
| 1，值 `0x01`–`0x10` | `OP_1` … `OP_16` —— 单字节 `0x51`…`0x60` |
| 1，值 `0x81` | `OP_1NEGATE` —— 单字节 `0x4f` |
| 1–75 | 单个长度字节 `0x01`–`0x4b`，随后是数据 |
| 76–255 | `OP_PUSHDATA1` —— `0x4c`，1 字节长度，随后是数据 |
| 256–65535 | `OP_PUSHDATA2` —— `0x4d`，2 字节小端长度，随后是数据 |
| ≥ 65536 | `OP_PUSHDATA4` —— `0x4e`，4 字节小端长度，随后是数据 |

说明：

- `1–75` 与 `OP_1`–`OP_16` 两行不会重叠。单字节且值为 `1`–`16` 时用操作码；其他任何单字节值用
  长度形式 `0x01 <byte>`。这个判断**只取决于那一次压栈的总长度**和**那一个字节的值** ——
  与更长载荷的内容毫无关系。
- `0x4e` 是最后一个承载长度的字节。`0x4f` 及以上的值是操作码。`0x75` 是个很好的例子：
  处在数据位置它表示"压入 117 字节"，处在指令位置它是 `OP_DROP`。**含义只由位置决定，
  字节本身没有固有类型。**
- 实现**禁止**产生非最短压栈，并且**必须**在解析时拒绝非最短压栈。

### 3.1 哪些字节可以出现在压栈位置

实现 `readPush` 时最容易出错的一处。**一个压栈位置的字节合法，当且仅当它属于下表之一**：

| 字节 | 含义 |
|---|---|
| `0x00` | `OP_0`，压入空 |
| `0x01`–`0x4b` | 长度 N，随后 N 字节数据 |
| `0x4c` / `0x4d` / `0x4e` | `OP_PUSHDATA1` / `2` / `4` |
| `0x4f` | `OP_1NEGATE`，压入 `0x81` |
| `0x51`–`0x60` | `OP_1`–`OP_16` |

**其余一切都是非法的**（解析器**必须**失败），其中要特别注意：

- **`0x50` = `OP_RESERVED`** —— 它**不是**长度字节，也不是有效操作码。
- **`0x4f`–`0x60` 这一段是断开的**：`0x4f` 有效、`0x50` 无效、`0x51`–`0x60` 有效。
  把 `0x4e` 当成"压栈字节的上界"是**错的**：`OP_1`…`OP_16` 都大于它。
- **`0x75` 与 `0xac`** 是操作码，出现在压栈位置即解析失败。

> **提示。** 把"压栈字节集合"实现成一个显式的区间判定，而不是
> `if op <= 0x4e { … } else { error }` 这样的单边假设。后者会静默拒掉所有 `OP_1`…`OP_16`。

## 4. 共识限制

| 限制 | 数值 | 对帧的约束 |
|---|---|---|
| 单次压栈的最大数据量 | **520 字节** | 单个字段**禁止**超过 520 字节。|
| 最大脚本长度 | **10 000 字节** | 整帧轻松容纳，帧从来不是限制因素。|

520 字节这个数字是本规范真正的**硬约束**，而且很硬：一个超过它的字段会生成一个
**永远没有任何矿工接受**的脚本 —— 如果构建器不做检查，这一切都是静默发生的。因此：

> 实现**必须**拒绝会导致脚本总长超过 520 字节的帧，并且**必须**拒绝任何长度超过 520 字节的字段。
> 它**必须**在产出输出**之前**就带着明确的错误信息拒绝。

需要超过 520 字节载荷的应用协议，**必须**选择：缩短它、对它取哈希、或者拆成多个帧。
见 [subprotocols/README.md](../subprotocols/README.md#5-超过-520-字节)。

**注（非规范）。** 10 000 字节的脚本限制对本核心鼓励的那类帧并不可达，因为 520 字节的单次压栈限制
对每个字段都生效。此处列出仅为完整性。

## 5. 元素字节预算

要在构建前算出帧的大小：

```
scriptLength = 1 + markerLength                    # marker 压栈（长度前缀 + 字节）
             + 1                                   # OP_DROP
             + Σ ( pushLength(fieldᵢ) + 1 )        # 每个字段压栈 + 它的 OP_DROP
             + 1 + 33                             # ownerPub 压栈
             + 1                                   # OP_CHECKSIG

pushLength(d) = 1 + d.length          若 d.length ≤ 75
              = 2 + d.length          若 d.length ≤ 255
              = 3 + d.length          若 d.length ≤ 65535
```

`OP_0` / `OP_1`–`OP_16` / `OP_1NEGATE` 这几种情况也都是 1 字节，上面的 `≤ 75` 那行已经覆盖。

应用协议应当公布自己的字节预算，让实现者不必重算。`bbs` 的 `v1-post` 公布了，见
[subprotocols/bbs/v1-post.md](../subprotocols/bbs/v1-post.md#3-字节预算)。
